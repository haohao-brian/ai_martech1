# 原則法制化管理系統
*Based on Taiwan Legal Hierarchy System*

## 法源位階 (Legal Hierarchy)

### 第一級：憲法層級原則 (Constitutional Level)
**相當於：中華民國憲法**
- 不可違反、不可變更的核心原則
- 修改需要特別程序（全體開發者同意）
- 例如：資料安全、系統穩定性、使用者隱私

### 第二級：法律層級原則 (Statutory Level)
**相當於：法律**
- 由團隊制定的標準規範
- 需要正式程序修改（PR review + 主管批准）
- 例如：架構模式、資料存取規則、命名規範

### 第三級：命令層級原則 (Regulatory Level)
**相當於：行政命令、法規命令**
- 實施細節和執行準則
- 可由技術負責人調整
- 例如：程式碼風格、文件格式、測試要求

### 第四級：行政規則 (Administrative Rules)
**相當於：行政規則、解釋令**
- 內部指導原則
- 可隨專案需求彈性調整
- 例如：開發流程、工具選擇、部署策略

### 第五級：慣例與判例 (Customs and Precedents)
**相當於：判例、習慣法**
- 團隊長期實踐形成的模式
- 可作為參考但非強制
- 例如：最佳實踐、經驗法則

## 法律原則對應

### 1. 法律不溯及既往原則
```yaml
principle: "新原則不影響既有程式碼"
implementation:
  - 新原則標記生效日期
  - 既有程式碼給予寬限期
  - 提供migration工具
example: |
  # EFFECTIVE_DATE: 2025-09-01
  # GRACE_PERIOD: 90 days
  # MIGRATION_TOOL: scripts/migrate_to_new_pattern.R
```

### 2. 特別法優於普通法原則
```yaml
principle: "特定情境原則優先於一般原則"
hierarchy:
  - 專案特定原則 > 部門原則 > 公司原則
  - 安全原則 > 效能原則 > 風格原則
example: |
  # 一般原則：使用 PostgreSQL
  # 特別原則：分析專案可使用 DuckDB
```

### 3. 法律明確性原則
```yaml
principle: "原則必須明確可執行"
requirements:
  - 明確定義適用範圍
  - 提供具體範例
  - 包含驗證方法
format: |
  ## 適用條件
  WHEN: [具體情境]
  THEN: [具體行動]
  EXCEPT: [例外情況]
```

### 4. 比例原則
```yaml
principle: "限制應與目的成比例"
evaluation:
  - 適當性：手段有助於目的達成
  - 必要性：沒有其他侵害較小的手段
  - 衡平性：手段與目的合乎比例
example: |
  # 目的：提升效能
  # 評估：犧牲可讀性是否值得20%效能提升？
```

### 5. 信賴保護原則
```yaml
principle: "開發者可信賴既定原則"
guarantees:
  - 原則變更需提前通知
  - 提供過渡期和支援
  - 不任意廢除已公布原則
process: |
  1. 預告期：30天
  2. 討論期：14天
  3. 過渡期：90天
```

## 衝突解決機制

### 法源位階解決
```yaml
當衝突發生時:
  1. 檢查法源位階：
     憲法級 > 法律級 > 命令級 > 規則級 > 慣例級
  
  2. 同級衝突時適用：
     - 特別法優於普通法
     - 新法優於舊法（但需注意信賴保護）
     - 明示其一排除其他
```

### 解釋權限
```yaml
層級解釋權:
  憲法級: CTO/架構師團隊
  法律級: 技術主管
  命令級: 專案負責人
  規則級: 資深開發者
  慣例級: 團隊共識
```

## 實施範例

### 範例一：資料庫存取原則
```yaml
# 原則編號：L2-001 (法律級)
名稱: 統一資料存取模式
位階: 法律級
制定機關: 架構團隊
生效日期: 2024-01-01
法源依據: 憲法級原則 L1-001（資料安全）

內容:
  第一條: 所有資料庫存取必須使用 tbl2() 函數
  第二條: 禁止直接使用 SQL 字串拼接
  第三條: 必須使用參數化查詢

罰則:
  違反第一條: Code Review 不通過
  違反第二條: 安全審查，可能觸發緊急修復
  違反第三條: 同第二條

例外:
  第四條: 效能關鍵路徑經審查可使用原生SQL
  第五條: 資料遷移腳本不在此限
```

### 範例二：函數組織原則
```yaml
# 原則編號：L3-021 (命令級)
名稱: 函數檔案組織規則
位階: 命令級  
制定機關: 開發團隊
生效日期: 2024-06-01
法源依據: 法律級原則 L2-005（程式碼組織）

內容:
  第一條: 主要函數應獨立成檔
  第二條: 檔名應與函數名稱對應
  第三條: 輔助函數可併入主函數檔案

但書:
  第四條: 調試期間得暫時合併相關函數
  第五條: 十行以下輔助函數不受第一條限制

施行細則:
  - 主要函數定義：公開API或超過50行
  - 調試期間定義：標記 #DEBUG 註解
  - 輔助函數定義：僅供單一主函數使用
```

## 修法程序

### 憲法級修改（最嚴格）
```yaml
程序:
  1. 提案: 需要 2/3 開發者連署
  2. 審議: 架構委員會審查
  3. 公告: 30 天公告期
  4. 表決: 需要 3/4 同意
  5. 實施: 90 天後生效
```

### 法律級修改（嚴格）
```yaml
程序:
  1. 提案: 技術主管或 1/3 開發者
  2. 審查: 技術委員會 review
  3. 公告: 14 天公告期
  4. 核准: 技術主管批准
  5. 實施: 30 天後生效
```

### 命令級修改（一般）
```yaml
程序:
  1. 提案: 任何開發者
  2. 討論: 團隊會議討論
  3. 決定: 專案負責人決定
  4. 實施: 7 天後生效
```

## 法律文件格式

### 標準原則文件模板
```markdown

## 法源資訊
- 位階：[憲法級/法律級/命令級/規則級/慣例級]
- 編號：[L1/L2/L3/L4/L5]-[序號]
- 制定：[制定單位] [日期]
- 修正：[歷次修正記錄]
- 施行：[生效日期]

## 法源依據
- 上位原則：[引用的上級原則]
- 授權依據：[獲得授權的來源]

## 本文
第一條 【條文標題】
  條文內容...

第二條 【條文標題】
  條文內容...
  
## 罰則
違反本原則之處理：
- 輕微：[處理方式]
- 一般：[處理方式]
- 嚴重：[處理方式]

## 附則
本原則自 [日期] 起實施
```

## 優點分析

### 1. 明確的權責劃分
- 每個層級都有明確的制定和解釋權限
- 避免原則制定的混亂

### 2. 穩定性與彈性平衡
- 核心原則穩定（憲法級）
- 實施細節彈性（命令級）

### 3. 程序正義
- 修改程序透明
- 保護開發者權益

### 4. 可預測性
- 開發者知道什麼能改、什麼不能改
- 變更有明確的程序和時程

### 5. 法治精神
- 規則明確，減少人治色彩
- 提供申訴和解釋機制
